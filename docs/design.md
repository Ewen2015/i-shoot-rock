# 界面与声音

视觉语言照 [typesafe.ai](https://typesafe.ai/)：纸 `#FEFEFE` / 墨 `#1E1E1E` /
粉 `#F386A1`。窗口是 Win95 那一套 —— 黑标题栏白字加三个方框按钮、灰面、2px 立体斜面、
**直角零圆角**，没有一个圆角。

标题压在半调点阵的抖动渐变天空条上。点阵用 canvas 现画（半径取覆盖度的平方根，
面积才和覆盖度成正比），密的「云堤」压在条子下半边并做成波浪边，上半边只留稀疏浮尘 ——
这样标题落在干净的粉底上，深色模式下标题也不会糊掉。天空条**不跟主题翻**：
它是招牌，就地钉住那套颜色，翻过去变成白点压在粉色上反而更难读。

**深色模式**：`prefers-color-scheme: dark` 翻转整套变量，跟随系统，不用手动切。
唯一的例外就是上面那条粉色天空。

## 倒计时：每一个数字都有它自己的那一声

3 / 2 / 1 各一声短促的「嘀」，数到 0 是一声低一点、带滑音的长音，屏幕上同时打出
「出拳！」—— **每一个声音都有一个数字配它**，不多出一声没来由的响。

声音用 Web Audio 现场合成，页面依然零外部依赖 —— 为三声「嘀」去加载一个 mp3 不划算。
浏览器要求先有一次用户手势才允许出声，所以第一次点击/按键时顺手解锁并预热音频设备
（新开的 `AudioContext` 要一两百毫秒才真的出得了声，第一声「嘀」正是卡在这段启动时间里）；
右上角那个 `♪` 按钮可以静音，静音是把总音量按到 0，已经排出去的声音也会立刻哑掉。

**数字和声音是同一刻到的**，这一条花了两轮才对。声音「排进去」是立刻的，但那一声要过
一段设备延迟才真的从扬声器出来（内置扬声器几十毫秒，蓝牙一两百毫秒，**AirPlay 两秒**），
屏幕却是马上画的 —— 于是耳朵听到的会落在眼睛看到的之后。声音没法提前，所以反过来让
画面跟着音频时钟走：四声一次排定，数字按同一张表画。

实测这台机器的默认输出一度是 AirPlay，Chrome 报 `outputLatency = 2.008` 秒 ——
**那不是乱报，是真的**。（第一版把它当成病态值截到 300ms，于是「还是不同步」。）

两个细节也是实测踩出来的：① 刚建出来的 `AudioContext` 会先报 `outputLatency = 0`，
几十毫秒后才是真值，而这几十毫秒正好压在「点开始」那一刻上，所以开数前最多等 250 毫秒
等它把真值说出来；② 上下文还是 suspended 时干脆不出声 —— 那种状态下 `currentTime` 是
冻住的，排进去的音会全挤在同一刻，等某次点击解开时一起炸出来。
设备延迟大到 400 毫秒以上时，屏幕上的「准备…」会写明白在等什么。

## 结算

**赢和输都有动画**，而且和音效同一刻：赢是粉色的半调点阵散成一圈、赢的那只手盖下来；
输是整张牌桌抖一下、墨色的细圈散开；平局两边一起跳。动画等音效那一段设备延迟，
开牌之后一起放 —— 所以 AirPlay 上会先看到结果、两秒后动画和声音同时到，
结算画面也跟着延长，不会把动画收走。

## 牌桌上的三处细节

- **「Jev 的判断」默认收着**。一局里真要看的只有两行：它猜你出什么、它出什么；
  概率条、期望净胜分和它收到的 `state` 原文都收进下面那个 fold 里，想深究再拉开
  （拉开的状态会记住，重画时不会被自动关上）。
- **「怎么说」写在牌桌上**，就在出拳按钮正下方那条 Win95 状态栏里（左边压一条粉色）。
  之前它缩在页面最底下的灰色小字里，没人会看见。
- **历史一直列在右下角**。每打完一局，双方的出拳和输赢都会追加进去，
  下一局开始时整段历史被写进 Jev 的 `state`。
